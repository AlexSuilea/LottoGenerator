## Architecture

The project is split into multiple small classes, each with a clear responsibility.

The main goal is to separate:

- ticket generation
- pricing
- diversification strategies
- statistical analysis
- simulation
- exact combinatorial analysis
- experimental portfolio optimization

> **Important:** no strategy in this project can predict future lottery draws or increase the jackpot probability of a single combination.  
> For the jackpot, the only way to increase the probability is to play more **distinct** combinations.

---

## `LottoGenerator`

Application entry point.

This class contains the `main()` method and orchestrates the different components of the application.

Depending on the experiment, it can:

- generate regular lottery tickets
- generate smart/diversified tickets
- run ticket analysis
- run simulations
- run exact combinatorial comparisons
- test portfolio optimization strategies

Example:

```java
List<List<Integer>> tickets =
        CombinatorialSmartTicketGenerator.generateTickets(
                10,
                10_000
        );
```

`LottoGenerator` should contain as little business logic as possible. Its responsibility is mainly to coordinate the other classes.

---

## `LottoMachine`

Core lottery utility class.

Responsible for basic random ticket generation and price calculation.

### Responsibilities

- Generates random Loto 6/49 tickets
- Generates random Loto 5/40 tickets
- Generates Joker tickets
- Uses `SecureRandom` for number generation
- Prevents identical generated tickets when used with a `Set`
- Calculates ticket costs
- Calculates transaction fees based on the number of physical/electronic slips
- Formats monetary values using `BigDecimal`

### Random generation

Tickets are generated by creating the complete number pool, shuffling it and selecting the required number of values.

Example:

```java
List<Integer> ticket =
        LottoMachine.generateTicket(6, 49);
```

### Pricing

The price calculation takes into account:

```text
variant cost
+
transaction fee per slip
```

For example, Loto 6/49 supports three zones per slip.

If four variants are played:

```text
4 × 8 RON
+
2 × 0.50 RON transaction fee

= 33 RON
```

`BigDecimal` is used instead of `double` to avoid floating-point precision problems when working with money.

## `SmartTicketGenerator`

Generates diversified Loto 6/49 tickets using a heuristic scoring system.

Instead of accepting the first random combination, the generator creates multiple candidate tickets and selects the highest-scoring candidate.

### Scoring criteria

The heuristic considers:

- total number sum
- odd/even distribution
- low/high number distribution
- spread between the smallest and largest number
- consecutive numbers
- overlap with previously selected tickets

Example:

```java
List<List<Integer>> tickets =
        SmartTicketGenerator.generateDiversifiedTickets(
                10,
                10_000
        );
```

This means that for every selected ticket, up to `10,000` random candidates are evaluated.

### Important

The balanced scoring system does **not** make an individual ticket more likely to win.

Its purpose is to generate a more diversified group of tickets and reduce unnecessary overlap between them.

## `CombinatorialSmartTicketGenerator`

Advanced ticket diversification strategy.

This is the preferred strategy when generating multiple Loto 6/49 tickets.

Instead of focusing mainly on visual properties such as odd/even distribution, this strategy focuses on **combinatorial coverage**.

### Optimization criteria

For each candidate ticket, the algorithm considers:

- previously unused numbers
- new 3-number subsets
- new 4-number subsets
- new 5-number subsets
- overlap with existing tickets

A ticket containing six numbers contains:

```text
C(6,3) = 20 triples
C(6,4) = 15 quadruples
C(6,5) = 6 five-number subsets
```

The generator attempts to avoid repeating these subsets unnecessarily.

Example:

```java
List<List<Integer>> tickets =
        CombinatorialSmartTicketGenerator.generateTickets(
                30,
                10_000
        );
```

### Observed behavior

For suitable portfolio sizes, the generator can produce:

```text
49/49 number coverage
maximum pairwise overlap <= 1
```

When two tickets share at most one number, they cannot share the same triple, quadruple or five-number subset.

This makes the portfolio highly diversified.

### Recommended usage

For multiple tickets, this is the main generation strategy currently recommended by the project.

## `TicketAnalyzer`

Analyzes the structure of a generated ticket portfolio.

It does not simulate lottery draws.

Instead, it measures how well the tickets are distributed.

### Metrics

The analyzer calculates:

- number of tickets
- number of distinct numbers covered
- percentage coverage of the 1–49 range
- average overlap between tickets
- maximum overlap between tickets
- frequency of every number

Example output:

```text
===== COMBINATORIAL SMART =====

Tickets: 10
Distinct numbers: 49/49
Coverage: 100.00%
Average overlap: 0.24
Maximum overlap: 1
```

This class is useful for comparing RANDOM and SMART strategies before running more expensive simulations.

## `LottoSimulator`

Monte Carlo simulation engine.

This class generates a large number of simulated Loto 6/49 draws and compares different ticket portfolios.

Example:

```java
LottoSimulator.runComparison(
        10,
        10_000,
        1_000_000,
        20260810L
);
```

Parameters:

```text
10          -> number of tickets
10,000      -> smart candidates per ticket
1,000,000   -> simulated lottery draws
20260810    -> reproducible random seed
```

### Output

For every simulated draw, the simulator determines the best result achieved by each portfolio:

```text
0/6
1/6
2/6
3/6
4/6
5/6
6/6
```

It also calculates:

```text
3+/6
4+/6
5+/6
6/6
```

### Reproducibility

The simulation uses a fixed seed so different strategies can be tested against the same pseudo-random sequence.

This is useful when testing changes to the ticket generation algorithms.

## `ExactLottoAnalyzer`

Exact mathematical analyzer for Loto 6/49 portfolios.

Unlike `LottoSimulator`, this class does **not** use random simulation.

It checks every possible Loto 6/49 draw.

The total number of combinations is:

```text
C(49,6) = 13,983,816
```

Therefore, the analyzer evaluates exactly:

```text
13,983,816 possible draws
```

Example:

```java
ExactLottoAnalyzer.compare(
        "COMBINATORIAL",
        combinatorialTickets,
        "OPTIMIZED",
        optimizedTickets
);
```

### Bitmask optimization

Each ticket is converted to a `long` bitmask.

The number of matching lottery numbers can then be calculated using:

```java
Long.bitCount(ticketMask & winningMask);
```

This makes the exact analysis significantly faster than repeatedly comparing Java collections.

### Why this class matters

Monte Carlo simulation produces estimates.

`ExactLottoAnalyzer` produces the exact result for a specific portfolio.

For example:

```text
6+/6 -> 10 tickets

10 / 13,983,816
≈ 0.0000715%
≈ 1 in 1,398,382
```

For ten distinct tickets, there will always be exactly ten possible jackpot draws.

## `PortfolioOptimizer`

Experimental hill-climbing optimizer.

This class attempts to improve an existing combinatorial portfolio for `3+/6` coverage.

It starts with an already diversified portfolio and repeatedly performs small mutations.

Example mutation:

```text
Before:
[6, 7, 8, 18, 27, 39]

Mutation:
27 -> 34

After:
[6, 7, 8, 18, 34, 39]
```

The mutation is accepted only when specific constraints are respected.

### Constraints

The optimizer tries to preserve:

- all 49 numbers covered
- no duplicate tickets
- maximum pairwise overlap <= 1
- good 3+/6 performance on the training sample

### Hill-climbing process

```text
Initial portfolio
       ↓
Random mutation
       ↓
Evaluate 3+/6 coverage
       ↓
Better?
  /          \
Yes          No
 ↓            ↓
Keep        Reject
```

### Experimental result

Testing revealed an important machine-learning-style problem:

**overfitting**.

The optimizer could achieve significantly higher `3+/6` coverage on its training sample, while exact evaluation across all `13,983,816` possible draws showed no real improvement and sometimes slightly worse performance.

Because of this, `PortfolioOptimizer` is kept as an experimental component rather than the recommended ticket-generation strategy.

It is also a useful demonstration of why performance on training data must always be validated against independent data.

## Current Recommended Strategy

For a single ticket:

```java
LottoMachine.generateTicket(6, 49);
```

There is nothing meaningful to diversify when only one combination is played.

For multiple tickets:

```java
CombinatorialSmartTicketGenerator.generateTickets(
        ticketCount,
        10_000
);
```

This attempts to maximize portfolio diversification while keeping ticket overlap low.

The other classes are primarily used for analysis and experimentation:

```text
LottoMachine
    ↓
basic random generation

SmartTicketGenerator
    ↓
balanced heuristic experiment

CombinatorialSmartTicketGenerator
    ↓
recommended multi-ticket strategy

TicketAnalyzer
    ↓
structural analysis

LottoSimulator
    ↓
Monte Carlo testing

ExactLottoAnalyzer
    ↓
exact evaluation of all 13,983,816 draws

PortfolioOptimizer
    ↓
experimental hill-climbing / overfitting study
```

## Mathematical Limitation

Regardless of the generation strategy, every individual Loto 6/49 combination has exactly the same jackpot probability:

```text
1 / 13,983,816
```

For `N` distinct tickets:

```text
P(jackpot) = N / 13,983,816
```

Therefore:

```text
1 ticket   ≈ 1 in 13,983,816
10 tickets ≈ 1 in 1,398,382
30 tickets ≈ 1 in 466,127
```

The algorithms in this project can reduce redundancy and improve portfolio coverage.

They cannot predict the future lottery draw.

## `GeneratorBenchmark`

Benchmarks the `CombinatorialSmartTicketGenerator` using different values for `candidatesPerTicket`.

The goal is to determine how many candidate tickets are actually necessary to produce a high-quality diversified portfolio without wasting CPU resources.

### Metrics

For every benchmark configuration, the class measures:

- average generation time
- average number coverage
- percentage of runs reaching `49/49` coverage
- percentage of runs where maximum pairwise overlap is `<= 1`

Example:

```java
GeneratorBenchmark.run(12);
```

This benchmarks portfolios containing 12 tickets using multiple candidate-search sizes.

Example configurations:

```text
1,000 candidates
5,000 candidates
10,000 candidates
25,000 candidates
50,000 candidates
100,000 candidates
```

Each configuration is executed multiple times in order to measure both performance and generation quality.

### Example Output

```text
========== GENERATOR BENCHMARK ==========
Tickets per portfolio: 12

Candidates   Runs     Avg time ms    Avg coverage   49/49 success   Overlap <= 1
1000         200      195.28         100.00%        100.00%         100.00%
```

### Benchmark Result

For a portfolio of 12 Loto 6/49 tickets, testing showed that:

```text
1,000 candidates per ticket
```

was already sufficient to achieve:

```text
100% average number coverage
100% of runs with 49/49 coverage
100% of runs with maximum overlap <= 1
```

Increasing the search size up to `100,000` candidates produced no measurable improvement in portfolio quality, while execution time increased significantly.

Example observed execution times:

```text
1,000 candidates   -> ~195 ms
5,000 candidates   -> ~950 ms
10,000 candidates  -> ~1.88 s
25,000 candidates  -> ~4.78 s
50,000 candidates  -> ~9.39 s
100,000 candidates -> ~18.78 s
```

Therefore, the current default for a 12-ticket portfolio is:

```java
private static final int DEFAULT_CANDIDATES_PER_TICKET = 1_000;
```

This provides a good balance between execution speed and portfolio quality.

### Warm-up

The benchmark performs several warm-up runs before measuring execution time.

This helps reduce the impact of JVM JIT compilation on the measured results.

### Important

This is a lightweight application-level benchmark using:

```java
System.nanoTime();
```

It is intended to compare practical configurations of this project.

For rigorous Java microbenchmarking, a framework such as JMH would be more appropriate.
